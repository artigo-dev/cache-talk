A cache is how a website remembers: it keeps the answer to an expensive question so the next visitor does not wait for it. That part is easy. The hard part is forgetting: the moment the answer changes, every cached page built from the old one has to go, and not a second too early or too late. This talk is the road of learning when to forget.Dzięki cache serwis pamięta: zapisuje odpowiedź na kosztowne pytanie, żeby następny użytkownik nie musiał na nią czekać. To akurat jest proste. Trudne jest zapominanie: kiedy odpowiedź się zmienia, każda strona w cache zbudowana na starej musi zniknąć – ani sekundy za wcześnie, ani sekundy za późno. Ta prezentacja to droga, na której uczymy się, kiedy zapominać.

Why do visitors wait while the cache forgets? Because the cache is busy. Redis does one thing at a time: while it deletes a million cached pages it answers nobody, so every visitor of every site on it waits (station 7). With files, the editor's "Save" hangs until thousands of files are deleted, and the busy disk slows every other request on that server (station 4).Dlaczego użytkownicy czekają, kiedy cache zapomina? One tag on 10 000 to 500 000 cached pages, forgotten in one invalidateTags() call. The file cache reads the tag's list and deletes every file on it, one at a time: the time grows in a straight line with the number of cached pages, about 6.4 µs a page. 100 000 pages: about 0.63 s; 500 000: about 3.5 s.Jeden tag na 10 000 do 500 000 stron w cache i jedno wywołanie invalidateTags(). Cache plikowy czyta listę tagu i kasuje z niej plik po pliku: czas rośnie liniowo z liczbą stron, mniej więcej 6,4 µs na stronę. 100 000 stron to około 0,63 s, 500 000 – około 3,5 s.

Why it grows: every cached page is its own file, and a file system has no "delete these 100 000". Each file is one delete (unlink), a call into the operating system that finds the name in the folder, removes it and frees the file's space. So the cost is the number of pages with the tag, not the size of the pages, and not how many other pages the cache holds.Skąd ten wzrost? Każda strona w cache to osobny plik, a system plików nie ma operacji „usuń te 100 000”. Każdy plik to osobne usunięcie (unlink), czyli wywołanie systemowe, które znajduje nazwę w katalogu, usuwa ją i zwalnia miejsce po pliku. Koszt zależy więc od liczby stron z tym tagiem – nie od ich rozmiaru i nie od tego, ile innych stron jest w cache.

A real run: Talk\Store\File, the files on tmpfs, in memory. On an SSD each delete costs more, on shared network storage (NFS) far more, and a site keeps more than one tag per page.To prawdziwy przebieg: Talk\Store\File, pliki na tmpfs, czyli w pamięci. -- one call forgets at most 7 500 cached pages
local function cache_unlink_by_tag(keys, args)
    local list, cursor = args[1], args[2]
    local bite = redis.call('HSCAN', list, cursor,
        'COUNT', 7500, 'NOVALUES')
    for _, id in ipairs(bite[2]) do
        redis.call('UNLINK', id)     -- the page goes
    end
    if #bite[2] > 0 then
        redis.call('HDEL', list, unpack(bite[2]))
    end
    return bite[1]    -- the next bite, '0': done
end

pub/subpublish and subscribe: clients wait on a channel, and one message to it wakes every one of them at once.publish/subscribe: klienci czekają na kanale, a jedna wiadomość budzi ich wszystkich naraz.

Five clicks, one step each. The first request finds no cached page and takes the lock: SET lock with a random token as its value, NX (only if Not eXists: Redis says OK to exactly one request) and PX 5000 (an expiry in milliseconds: a crashed holder's lock is gone after 5 s). One command, so nothing gets between "is it free?" and "take it". The others find it taken and subscribe to the lock's channel, on a connection of their own (a subscribed connection can do nothing else). They wait for a message, not on a timer.Pięć kliknięć, każde to jeden krok. Pierwsze żądanie trafia na cache miss i bierze blokadę: SET lock z losowym tokenem jako wartością, NX (Not eXists – tylko jeśli klucz nie istnieje, więc Redis odpowie OK dokładnie jednemu żądaniu) i PX 5000 (TTL w milisekundach: jeśli właściciel padnie, jego blokada zniknie po 5 s). To jedno polecenie, więc nic się nie wciśnie między „czy wolna?” a „biorę”. Pozostałe zastają blokadę zajętą i subskrybują jej kanał, na osobnym połączeniu (połączenie w trybie subskrypcji nie może robić nic innego). Czekają na wiadomość, a nie na zegar.

The first asks the database and saves the cached page, then releases with one Lua call: is the lock still mine (the token)? Then PUBLISH, then DEL. If the first one crashes, nobody publishes: its lock expires after lock_ttl_ms (2 s by default, 5 s in this talk's config), no waiter waits longer than the lock can still live, and one of them takes the lock and builds the cached page. Be honest about the trade: memory comes back later, and other servers learn about a change within a second, not instantly.Tu trzeba uczciwie powiedzieć, co za to płacimy: pamięć odzyskujemy później, a inne serwery dowiadują się o zmianie w ciągu sekundy, nie od razu.

Where the second comes from: rules_cache_ms, 1 000 ms by default, and it is the worst case: another server sees the edit between 0 and 1 s later, depending on how old its copy is. A "server" here is one APCu pool, the PHP workers that share it; on the same pool the edit counts at once, because the worker that made it puts the new rule into the shared copy. Without the shared copy (rules_shared_cache: no) every process waits on its own. On a single server there is no lag for an edit made through the web: the copy holds the rule at once, and a worker whose copy may lack an invalidation made on its server never serves from it (it reloads, or misses and rebuilds). The one exception there is the CLI (a cron job, an import): it has its own APCu, so to the web workers it is another server, at most a second away. Every server holds a copy of the rules in APCu and reloads it from Redis once that copy is a second old. php-library's own example: server web2 loads its copy at 11:59:59.600; at 12:00:00.000 an edit on web1 invalidates the tag product:7, and web1's next read is a miss at once (it added the rule itself); web2 still serves the old cached page until 12:00:00.600, when its copy is a second old and the next read reloads it. Exact reads (rules_cache_ms: 0) close the gap and read the rules on every fetch.Skąd ta sekunda: z rules_cache_ms, domyślnie 1 000 ms, i to jest najgorszy przypadek: inny serwer widzi edycję po czasie od 0 do 1 s, zależnie od tego, jak stara jest jego kopia. „Serwer” to tutaj jedna pula APCu, czyli workery PHP, które ją współdzielą; w obrębie tej samej puli edycja działa od razu, bo worker, który ją zrobił, sam wpisuje nową regułę do wspólnej kopii. Bez wspólnej kopii (rules_shared_cache: no) każdy proces czeka osobno. Na pojedynczym serwerze edycja zrobiona przez WWW nie ma żadnego opóźnienia: kopia od razu zawiera regułę, a worker, którego kopii może brakować unieważnienia zrobionego na jego serwerze, nigdy z niej nie serwuje (przeładowuje ją albo uznaje odczyt za cache miss i buduje stronę od nowa). Jedyny wyjątek to CLI (cron, import): ma własne APCu, więc dla workerów WWW jest innym serwerem, z opóźnieniem najwyżej sekundy. Każdy serwer trzyma kopię reguł w APCu i przeładowuje ją z Redisa, gdy kopia ma sekundę. Przykład wprost z php-library: serwer web2 ładuje swoją kopię o 11:59:59.600; o 12:00:00.000 edycja na web1 unieważnia tag product:7 i następny odczyt na web1 od razu kończy się cache miss (web1 sam dodał regułę); web2 dalej serwuje starą stronę z cache do 12:00:00.600 – wtedy jego kopia ma sekundę i następny odczyt ją przeładowuje. Dokładne odczyty (rules_cache_ms: 0) zamykają tę lukę i czytają reguły przy każdym pobraniu.

The cleanup: every invalidation adds its rule and trims the stream in the same Lua call (XTRIM MINID, now minus rules_retention_s): rules older than 30 days go, since no cached page may live longer (a longer TTL is capped to it) and an older rule can match nothing. A full clear keeps only itself. The stream has no expiry of its own (PERSIST). If nobody invalidates anything for weeks, the old rules wait for the next edit, harmlessly. Each server's copy keeps only the newest rule per tag, at most rules_max_tags (15 000) of them.Sprzątanie: każde unieważnienie dodaje swoją regułę i w tym samym wywołaniu Lua przycina stream (XTRIM MINID, teraz minus rules_retention_s): reguły starsze niż 30 dni wylatują, bo żadna strona nie może żyć w cache dłużej (dłuższy TTL jest przycinany do tego limitu), więc starsza reguła do niczego już nie pasuje. Po pełnym czyszczeniu w streamie zostaje tylko jego własna reguła. Stream nie ma własnego TTL (PERSIST). Jeśli przez tygodnie nikt niczego nie unieważnia, stare reguły czekają na następną edycję – i nikomu nie szkodzą. Kopia na każdym serwerze trzyma tylko najnowszą regułę dla każdego tagu, najwyżej rules_max_tags (15 000).

How the rules could be lost: allkeys-* eviction, a FLUSHALL or DEL by hand, a failover to a replica without the newest rules, a cluster slot lost with its node. The store notices: a rule that opens a new stream is marked as the first, and a cached page stamped with a rule the stream no longer holds is a miss.Jak reguły mogą przepaść: eviction w trybie allkeys-*, ręczny FLUSHALL albo DEL, failover na replikę, która nie ma najnowszych reguł, slot klastra stracony razem z węzłem. Store to zauważy: reguła, która zaczyna nowy stream, jest oznaczona jako pierwsza, a strona ze znacznikiem reguły, której w streamie już nie ma, to cache miss.

How the system remembers. A deleted cached page (delete(), or a write-through) does not just vanish: in one Lua step its key is replaced by a tombstone, a tiny hash holding only "epoch", a random token, with an expiry of invalidation_window_ms (60 s by default). The save that follows lands only if the key's token is still the one its miss saw: a delete in between left another token, and the late save is refused.Jak system pamięta. The two locks differ in what the lock is made of. Both give one rebuild for every server (measured: 1 origin call for 12 requests on 12 servers). MemoLock keeps it in Redis, with SET NX PX, and wakes the others with a message: 4 ms behind the request that has the lock; it needs Redis and a second connection, and it alone locks things that are not cached pages (once(), exclusively()). FleetLock takes any symfony/lock store: no Redis needed, one lock story for the whole application, one connection. The price is the Lock component's wake-up: a 100 ms poll on most stores (108 ms behind), not on PostgreSQL, which blocks natively, nor on the package's PubSubRedisStore (7 ms).Te dwie blokady różnią się tym, na czym są zbudowane. Obie dają jedną przebudowę na wszystkie serwery (zmierzone: 1 wywołanie origin na 12 żądań z 12 serwerów). MemoLock trzyma blokadę w Redisie, przez SET NX PX, i budzi resztę wiadomością: 4 ms za żądaniem, które ma blokadę; potrzebuje Redisa i drugiego połączenia, i tylko on potrafi blokować rzeczy, które nie są stronami w cache (once(), exclusively()).
