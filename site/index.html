A cache is how a website remembers: it keeps the answer to an expensive question so the next visitor does not wait for it. That part is easy. The hard part is forgetting: the moment the answer changes, every cached page built from the old one has to go, and not a second too early or too late. This talk is the road of learning when to forget.Dzięki cache serwis pamięta: zapisuje odpowiedź na kosztowne pytanie, żeby następny odwiedzający nie musiał na nią czekać. To akurat jest proste. Trudne jest zapominanie: kiedy odpowiedź się zmienia, każda strona w cache wygenerowana ze starej musi zniknąć – ani sekundy za wcześnie, ani sekundy za późno. Ta prezentacja to droga, na której uczymy się, kiedy zapominać.

Forgetting a tag means finding and deleting every file that carries it. With a hundred cached pages that is nothing; with twenty thousand it takes a while. And every server keeps its own files: with several servers, each holds its own copy of those twenty thousand, while the edit reaches only the server it was saved on. One tag on 10 000 to 500 000 cached pages, forgotten in one invalidateTags() call. The file cache reads the tag's list and deletes every file on it, one at a time: the time grows in a straight line with the number of cached pages. The same pages twice: in memory about 6.8 µs a page (100 000 pages: 0.65 s; 500 000: 3.35 s), on disk about 17.4 µs a page (1.74 s; 8.82 s).Jeden tag na 10 000 do 500 000 stron w cache i jedno wywołanie invalidateTags(). Cache plikowy czyta listę tagu i kasuje z niej plik po pliku: czas rośnie liniowo z liczbą stron. Te same strony dwa razy: w pamięci około 6,8 µs na stronę (100 000 stron to 0,65 s, 500 000 – 3,35 s), na dysku około 17,4 µs na stronę (1,74 s i 8,82 s).

Why it grows: every cached page is its own file, and a file system has no "delete these 100 000". Each file is one delete (unlink), a call into the operating system that finds the name in the folder, removes it and frees the file's space. So the cost is the number of pages with the tag, not the size of the pages, and not how many other pages the cache holds.Skąd ten wzrost? Każda strona w cache to osobny plik, a system plików nie ma operacji „usuń te 100 000”. Każdy plik to osobne usunięcie (unlink), czyli wywołanie systemowe, które znajduje nazwę w katalogu, usuwa ją i zwalnia miejsce po pliku. Koszt zależy więc od liczby stron z tym tagiem – nie od ich rozmiaru i nie od tego, ile innych stron jest w cache.

A real run, the same pages on two media in turn: tmpfs, in memory, the best case; and the laptop's SSD (ext4, the disk of Docker's VM). On the disk every delete costs about 2.6 times as much, on shared network storage (NFS) far more, and a site keeps more than one tag per page.To prawdziwy przebieg, te same strony na dwóch nośnikach po kolei: na tmpfs, czyli w pamięci – najlepszy przypadek; i na SSD laptopa (ext4, dysk maszyny wirtualnej Dockera). Na dysku każde usunięcie kosztuje około 2,6 raza więcej, na współdzielonym dysku sieciowym (NFS) dużo więcej – a w prawdziwym serwisie strona ma więcej niż jeden tag.

One builds, the others are wokenJeden generuje, reszta się budzi

pub/subpublish and subscribe: clients wait on a channel, and one message to it wakes every one of them at once.publish/subscribe: klienci czekają na kanale, a jedna wiadomość budzi ich wszystkich naraz.

Five clicks, one step each. The first request finds no cached page and takes the lock: SET lock with a random token as its value, NX (only if Not eXists: Redis says OK to exactly one request) and PX 5000 (an expiry in milliseconds: a crashed holder's lock is gone after 5 s). One command, so nothing gets between "is it free?" and "take it". The others find it taken and subscribe to the lock's channel, on a connection of their own (a subscribed connection can do nothing else). They wait for a message, not on a timer.Pięć kliknięć, każde to jeden krok. Pierwsze żądanie trafia na cache miss i zakłada locka: SET lock z losowym tokenem jako wartością, NX (Not eXists – tylko jeśli klucz nie istnieje, więc Redis odpowie OK dokładnie jednemu żądaniu) i PX 5000 (TTL w milisekundach: jeśli właściciel padnie, jego lock zniknie po 5 s). To jedno polecenie, więc nic się nie wciśnie między „czy wolna?” a „biorę”. Pozostałe zastają locka zajętego i subskrybują jego kanał, na osobnym połączeniu (połączenie w trybie subskrypcji nie może robić nic innego). Czekają na wiadomość, a nie na zegar.

A clock is used, but only one: the ids are the time of the Redis node that holds the stream, and Redis never gives an id lower than the last, even if its clock steps back. What is never done is comparing two clocks: a PHP server's with another's, or one node's with another's. Trimming by age uses that same clock, the newest id minus 30 days.Zegar jest w użyciu, ale tylko jeden: identyfikatory to czas węzła Redisa, który trzyma stream, a Redis nigdy nie nada identyfikatora niższego od poprzedniego, nawet gdy jego zegar się cofnie. Nigdy za to nie porównuje się dwóch zegarów: serwera PHP z innym serwerem ani węzła z innym węzłem. Przycinanie według wieku korzysta z tego samego zegara: najnowszy identyfikator minus 30 dni.

Why not something simpler. A list has no ids, only positions, and they shift when it is trimmed. A sorted set needs a score from the caller: a PHP server's clock, or a counter kept in a second key. A hash with the newest version per tag cannot be asked "what changed since", so a server would copy all of it, or a read would ask Redis for its tags' versions (that is Symfony's TagAwareAdapter). The stream gives all three on the slide in one key. Figures: with 10 000 rules, reading them all is 619 KB and 21.8 ms, reading what is new 3.5 KB and 2.2 ms; 15 000 rules take 527 KB as a stream, 990 KB as a hash. A stream in production: 1 849 rules, 59 KB. It is the plainest use of a stream (XADD, XRANGE, XTRIM): no consumer groups, no blocking read, since a PHP-FPM worker lives for one request and nobody is there to listen.Dlaczego nie coś prostszego. How an id that exists on one node works for pages on all of them: the nodes never talk to each other about it, PHP carries it. PHP reads the rules from the node that has the stream and keeps them in APCu. When it saves a page, on whichever node that page belongs to, it writes the newest rule id it holds into the page as its stamp: an id is just a value, like the page's tags. When it reads the page back, from that same node, it gets the stamp with it and compares it with its copy of the rules, in PHP. So Redis node B never needs to know what node A has.Jak identyfikator, który istnieje na jednym węźle, działa dla stron na wszystkich: węzły w ogóle o nim ze sobą nie rozmawiają, przenosi go PHP. PHP czyta reguły z węzła, na którym leży stream, i trzyma je w APCu. Gdy zapisuje stronę – na tym węźle, na który ta strona trafia – wpisuje do niej jako stempel identyfikator najnowszej reguły, którą zna: identyfikator to zwykła wartość, tak jak tagi strony. The cluster. Every key lives on one node, and a call may touch only keys of one node (one slot). The cached pages are spread over all the nodes, each with its own clock; the rules stream is one key, so one node makes every rule's id, and a page's stamp is such an id too. Nothing compares one node's clock with another's. Adding a rule and trimming the old ones is one call on that one key. A page is written on another node than the rules, so its write cannot read the stream in the same call: it is stamped with the newest rule id its server already holds, which can only make the page outdated sooner, never fresh by mistake. The one place clocks matter: a failover that loses the newest rules. Be honest about the trade: memory comes back later, and other servers learn about a change within a second, not instantly.Tu trzeba uczciwie powiedzieć, co za to płacimy: pamięć odzyskujemy później, a inne serwery dowiadują się o zmianie w ciągu sekundy, nie od razu.

Where the second comes from: rules_cache_ms, 1 000 ms by default: another server usually sees the edit between 0 and 1 s later, depending on how old its copy is (README.CACHE promises within rules_cache_ms + 1 s, since a copy may still be used while another worker reloads it). A "server" here is one APCu pool, the PHP workers that share it; on the same pool the edit counts at once, because the worker that made it puts the new rule into the shared copy. Without the shared copy (rules_shared_cache: no) every process waits on its own. On a single server there is no lag for an edit made through the web: the copy holds the rule at once, and a worker whose copy may lack an invalidation made on its server never serves from it (it reloads, or misses and rebuilds). The one exception there is the CLI (a cron job, an import): it has its own APCu, so to the web workers it is another server, at most a second away. Every server holds a copy of the rules in APCu and reloads it from Redis once that copy is a second old. php-library's own example: server web2 loads its copy at 11:59:59.600; at 12:00:00.000 an edit on web1 invalidates the tag product:7, and web1's next read is a miss at once (it added the rule itself); web2 still serves the old cached page until 12:00:00.600, when its copy is a second old and the next read reloads it. Jedyny wyjątek to CLI (cron, import): ma własne APCu, więc dla workerów WWW jest innym serwerem, z opóźnieniem najwyżej sekundy. The cleanup: every invalidation adds its rule and trims the stream in the same Lua call (XTRIM MINID, now minus rules_retention_s): rules older than 30 days go, since no cached page may live longer (a longer TTL is capped to it) and an older rule can match nothing. A full clear keeps only itself. The stream has no expiry of its own (PERSIST). If nobody invalidates anything for weeks, the old rules wait for the next edit, harmlessly. StaleCache wraps the pool, because serving a stale value needs the value's own times, which a callback wrapper never sees; it uses the same MemoLock to pick the one process that refreshes. setDeferrer() with a RefreshQueue moves that refresh after the response: flushAtShutdown() runs the queue at the end of the script, once Symfony's Response::send() has finished the request (in a bare PHP script call fastcgi_finish_request() first; in a full application TerminateSubscriber can run the queue on kernel.terminate instead). Without a deferrer, the refreshing request waits for its own rebuild. The two locks differ in what the lock is made of. Both give one rebuild for every server (measured: 1 database call for 12 requests on 12 servers). MemoLock keeps it in Redis, with SET NX PX, and wakes the others with a message: 3 ms behind the request that has the lock in the stampede demo (4 ms in the package's own benchmark, where the 108 ms and 7 ms below come from); it needs Redis and a second connection, and it alone locks things that are not cached pages (once(), exclusively()). FleetLock takes any symfony/lock store: no Redis needed, one lock story for the whole application, one connection. The price is the Lock component's wake-up: a 100 ms poll on most stores (108 ms behind), not on PostgreSQL, which blocks natively, nor on the package's PubSubRedisStore (7 ms).Te dwa locki różnią się tym, na czym są zbudowane.
